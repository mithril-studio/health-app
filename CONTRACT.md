# Coach Reachy implementation contract

Manual running scores: `GET /api/athlete-scores` returns `{lt1_hr, lt2_hr, vo2max, hr_zones, updated_at}`.
Authenticated `POST /api/athlete-scores` replaces the three score fields; each is required
but nullable to clear it. HR values are integers 30–250 bpm, LT1 < LT2 when both are set,
and VO2max is 5–100 ml/kg/min. Scores persist independently of sync, appear in every new
coach context, and saved running LT2 overrides the LTHR proxy in running analysis.
The user edits scores in Settings → Zones & scores; no agent write tool is exposed for them.
Optional `hr_zones` is an ordered list of five `{min_bpm, max_bpm}` inclusive Z1–Z5
ranges with integer limits from 30–250, no gaps or overlaps. Null clears zones; omission
preserves them. Saved zones reach each coach context and are used to calculate personal
time-in-zone metrics from running HR streams, with missing/out-of-range coverage explicit.

Backend FastAPI at 127.0.0.1:8001. Next.js serves UI on port 3000; nginx public 8000 routes /api/* and /mcp to backend, everything else to Next. Postgres cache. No public health data. UI login with APP_PASSWORD (generated secret), session HttpOnly Secure SameSite strict cookie; API accepts session or dedicated bearer tokens. UI calls same-origin API. GET /api/dashboard?oldest=YYYY-MM-DD&newest=YYYY-MM-DD returns {activities: [], events: [], wellness: [], fitness: [], settings: {}, sync: {last_success, error}, insights: {}}; raw Intervals records preserved. activity fields id,name,type,start_date_local,moving_time,distance,icu_training_load,average_heartrate,icu_average_watts,icu_zone_times,hr_zone_times,pace_zone_times. Events fields id,name,type,start_date_local,moving_time,description,category,paired_activity_id. Wellness id date,hrv,sleepSecs,restingHR,weight,ctl,atl. Fitness records date,ctl,atl,form. GET /api/activity/{id} -> raw activity + intervals. POST /api/sync -> sync status. GET /api/curves?sport=Run&period=84 -> raw curves. POST /api/chat {message:string,conversation_id?:string} -> {reply:string}; GET /api/chat?conversation_id=web -> {messages:[{role,content,created_at}]}. Conversation IDs are `web` (preserved legacy history) or `web:<32 lowercase hex digits>`, and must exist. GET /api/conversations -> {conversations:[{id,title,updated_at}]} (100 most recent); POST /api/conversations {} -> a new conversation (201). Titles come from the first user message, not a generated summary; each conversation has separate agent context and message history. POST /api/tools/{name} tool arguments -> result. POST /api/login {password} -> session cookie; GET /api/session -> {authenticated:boolean,cookie_received:boolean}; POST /api/logout. UI render login when unauthenticated. All app data APIs protected, /api/session and /api/login public. GET /api/health only generic readiness. POST /api/internal/telegram raw update and POST /api/internal/job {kind:'morning'|'evening'|'activity',key:string,activity_id?:string} guarded BOX_SHARED_SECRET bearer. Worker always sends stable idempotency key. MCP /mcp uses MCP_AUTH_TOKEN bearer, official SDK Streamable HTTP; same tools as agent. Tools: get_calendar(oldest,newest), get_activity(id), get_activity_analysis(id,lt2_hr?,offset?,limit?), get_fitness(oldest,newest), get_wellness(oldest,newest), get_curves(sport,period), plan_workout(date,name,sport,description), move_workout(id,date), update_workout(id,name?,description?), delete_workout(id) returns pending confirmation; confirms only via user-facing dedicated endpoint/button, never model-supplied boolean; update_zones(sport,threshold_pace?,ftp?,hr_zones?). Agent writes must be audited + echoed to Telegram. System timezone Europe/Amsterdam, runs Mon/Tue/Thu/Sun plus football/gym, 5km sub18 then sub17 goals. Missing data never invented.
